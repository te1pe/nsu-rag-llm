# Как составить вопросы для оценки

Все цифры качества в проекте — recall поиска, верность и полнота ответов,
точность отказов, сравнение моделей, агент против конвейера — считаются по
`eval/questions.jsonl`. Этот файл пишете вы, и только вы: вопросы, которые
сочинила бы сама система, измеряли бы систему её же мерками, и результат ничего
бы не значил. Здесь — всё, чтобы писать их быстро и так, чтобы цифрам можно было
верить.

## Что получится

60 вопросов. Заготовка `eval/questions.skeleton.jsonl` уже расставила id, курсы
и типы — остаётся заполнить текст, `gold` и эталонный ответ.

| id | курсы | зачем |
|---|---|---|
| q001–q050 | по 10 на каждый курс MVP: `lop`, `matan`, `os`, `tvims`, `vychmat` | основная оценка: поиск, ответы, модели, агент |
| q051–q060 | по одному на курсы вне MVP: `bd`, `diskretka`, `eltech`, `evm`, `linal`, `matlog`, `proga`, `seti`, `shemotehnika`, `tfkp-diffury` | что даёт полный корпус (фаза 4.5) |

В каждом курсе MVP: 3 `factual`, 3 `definition`, 2 `comparison`, 1 `multi_hop`,
1 `unanswerable`. Распределение можно менять — это план, не правило; меньше 50
вопросов делают доверительный интервал шире, чем разница между режимами поиска.

## Порядок работы

1. Скопируйте заготовку:

       cp eval/questions.skeleton.jsonl eval/questions.jsonl

2. Один курс за раз. Откройте свои конспекты и методички, вспомните, что
   спрашивали на экзаменах и что вы сами искали, готовясь, — из этого и
   получаются хорошие вопросы.
3. Для каждой строки: сформулируйте вопрос, найдите ответ в методичке, запишите
   `gold` (файл и страницы) и `reference_answer`.
4. После каждого курса проверьте файл:

       uv run nsu-rag eval --stage retrieval --validate-only

   Валидатор назовёт строку и поле с ошибкой, проверит, что файл существует и
   страница в нём есть, и предупредит, если документа нет в индексе.

## Как писать `gold`

* **`file`** — путь относительно `data/raw/`: `os/sem4/<файл>.pdf`.
* **`pages`** — номер страницы в PDF-файле, считая с 1: то, что показывает поле
  номера страницы в просмотрщике, **а не число, напечатанное на странице**. Они
  расходятся, когда перед текстом обложка и оглавление (ADR-011).
* Ответ на двух страницах — укажите обе: `[34, 35]`.
* **Быстрый способ** — найти фразу из ответа:

      uv run nsu-rag find "фраза из учебника"
      uv run nsu-rag find "фраза" --course os

  Команда покажет файл в том виде, в каком он нужен для `gold`, номер страницы
  и в каком индексе документ (`mvp`, `full`). Она ищет и в сканах, где поиск
  просмотрщика не работает: текст распознан нашим OCR. Ищет точную фразу
  (регистр и `ё` не важны) — берите 3–6 слов подряд, без формул.
* Для q001–q050 документ должен быть в индексе `mvp`, иначе поиск MVP его не
  найдёт и вопрос станет промахом по определению.
* **Не выбирайте страницу по выдаче `nsu-rag search` или `nsu-rag ask`.** Это та
  самая система, которую мы оцениваем: `gold` должен говорить, где ответ на
  самом деле, по вашему знанию, а не где его нашёл поиск.

## Как писать каждый тип

**`factual`** — конкретный факт с коротким ответом.
«Какой … используется для …?», «Сколько …?», «Какой системный вызов …?»,
«В каком случае …?»

**`definition`** — определение понятия.
«Что такое X?», «Что называется X?», «Дайте определение X.»

**`comparison`** — различие двух понятий.
«Чем X отличается от Y?», «В чём разница между X и Y?». Оба понятия должны быть
в методичках; если они в разных главах или книгах — это уже `multi_hop`.

**`multi_hop`** — ответ собирается из двух мест: двух разделов, двух книг.
«Как X связан с Y?», «Почему X, если учесть Y?». В `gold` — оба источника,
каждый со своими страницами; recall такого вопроса частичный, если найден
только один.

**`unanswerable`** — правдоподобный вопрос по теме курса, ответа на который
в методичках **нет**. `gold` пустой, эталон — «В методичках этого нет.» (уже
в заготовке). Хорошие варианты:
* соседняя тема, которую курс не проходил;
* слишком конкретная деталь: версия программы, год, имя, которых в тексте нет;
* вопрос с ложной посылкой («почему X всегда быстрее Y», когда это не так).

Проверьте ключевые слова через `nsu-rag find`: если они нашлись, ответ,
возможно, всё-таки есть. Именно на этих вопросах настраивается порог отказа
агента (`AGENT_MIN_SCORE`), поэтому правдоподобность важнее экзотики: вопрос
про футбол модель отклонит и так.

## Чего избегать

* **Не копируйте формулировку из учебника.** BM25 найдёт такой вопрос по
  совпадению слов, и recall окажется завышенным. Пишите так, как спросили бы
  на экзамене или в чате с одногруппником. Часть вопросов — с синонимами и
  сокращениями, которых нет в тексте.
* **Не делайте ответом формулу.** Парсер заменил формулы маркером `[формула]`
  (ADR-012): такой вопрос измерит парсер, а не поиск.
* **Не проверяйте вопросы через систему, пока не записали `gold`** — это
  подгонка ответа под задачу.
* Не берите всё из первых глав: ответы должны быть разбросаны по книгам.
* Не спрашивайте «перескажи главу»: top-k поиск на это не рассчитан, это
  ограничение проекта, а не то, что стоит мерить.

## Эталонный ответ

1–3 предложения **своими словами** с ключевыми утверждениями. Судья проверяет
полноту именно по ним: «все ли ключевые утверждения эталона есть в ответе».
Не копируйте абзацы из методички: `questions.jsonl` лежит в репозитории, а
тексты методичек в нём быть не должны.

## Полный корпус (q051–q060) и два индекса

На MVP-индексе эти вопросы — промахи: так и задумано, они показывают, что даёт
полный. Сравнивайте индексы на q001–q050 отдельно и на всём файле:

    uv run nsu-rag eval --stage retrieval
    uv run --env-file corpus.full.env nsu-rag eval --stage retrieval

По желанию: добавьте пары «тот же вопрос по-русски и по-английски» с одним
`gold` в английском документе (q061 и дальше). Они измерят языковой барьер,
найденный в фазе 4.5: русские вопросы почти не доходят до английских
справочников (ADR-030).

## Запуск оценки

    uv run nsu-rag eval --stage retrieval      # recall@5/10, MRR@10, четыре режима
    uv run nsu-rag eval --stage generation     # модели из eval/models.yaml, с судьёй
    uv run nsu-rag eval --stage agent          # агент против конвейера фазы 3

Отчёты — в `eval/reports/`: только id и числа, их можно коммитить.

## Ручная разметка — после первого прогона `generation`

Судье можно верить настолько, насколько он совпадает с вами. После прогона
в каждой папке `data/eval-runs/<прогон>/` есть `review.md`: вопрос, эталон,
ответ модели и фрагменты, которые она читала. Прочитайте 30 ответов и запишите
в `eval/manual_labels.jsonl` (формат — `eval/manual_labels.example.jsonl`):

* **`faithful`** — каждое утверждение ответа есть во фрагментах. Верное по
  сути, но взятое не из фрагментов — `false`.
* **`complete`** — ответ покрывает ключевые утверждения эталона.
* `note` — по желанию, своими словами.

Затем:

    uv run nsu-rag eval --stage judge

покажет совпадение с судьёй и каппу Коэна. Каппа выше 0,6 — судье можно
доверять; около 0 — он угадывает, и тогда стоит сменить модель судьи
(`JUDGE_MODEL`, `JUDGE_BASE_URL`).
