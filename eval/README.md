# Вопросы для оценки

> Как их писать: пошаговое руководство [QUESTIONS_GUIDE.md](QUESTIONS_GUIDE.md)
> и скелет на 60 позиций для заполнения — `questions.skeleton.jsonl`.

`questions.jsonl` пишет автор, по одному JSON-объекту на строку, и никто
больше: вопросы, сгенерированные проверяемой системой, ничего бы не измеряли.
`questions.example.jsonl` показывает формат на двух заглушках.

| поле | смысл |
|---|---|
| `id` | уникальный, например `q001` |
| `course` | слаг курса, к которому относится вопрос: `os`, `matan`, `tvims`… |
| `question` | так, как спросил бы студент |
| `type` | `factual`, `definition`, `comparison`, `multi_hop` или `unanswerable` |
| `gold` | где находится ответ: `[{"file": ..., "pages": [...]}]`; для `unanswerable` пусто |
| `reference_answer` | ответ своими словами |

* `file` — путь **относительно `data/raw/`**, как в `data/courses.yaml`:
  `os/sem4/<file>.pdf`.
* `pages` — номера страниц **PDF-файла, начиная с 1** (то, что показывает поле
  страницы в просмотрщике), а не номер, напечатанный на странице. Они
  расходятся всякий раз, когда в начале идёт обложка или оглавление (ADR-011).
* Ответ на вопрос `multi_hop` собирается из двух и более мест: перечислите
  каждое.
* Найти можно только документы, которые есть в индексе; валидатор
  предупреждает об эталонном файле, которого там нет (вне MVP или скан).

Полезный набор — хотя бы ~50 вопросов: по 10 на каждый курс MVP, смесь типов и
около пяти `unanswerable`, которые звучат правдоподобно, но в методичках
ответа на них нет. При меньшем числе доверительный интервал в отчёте шире, чем
разница между режимами поиска.

    uv run nsu-rag eval --stage retrieval --validate-only   # проверить файл
    uv run nsu-rag eval --stage retrieval                   # все четыре режима

Отчёты пишутся в `reports/<date>-retrieval.md` и содержат только id вопросов и
метрики — ни текста вопросов, ни цитат из методичек, — поэтому их можно
коммитить.

## Оценка ответов (фаза 4)

    uv run nsu-rag eval --stage generation                     # все модели из models.yaml
    uv run nsu-rag eval --stage generation --variants qwen3.5-9b --no-judge

Каждый вопрос ищется один раз (`RETRIEVAL_MODE`, без фильтра по курсу — так, как
спросил бы студент), и все модели из `models.yaml` отвечают по одним и тем же
фрагментам, пока остальные выгружены из памяти. Затем судья (настройки
`JUDGE_*`) читает каждый ответ дважды: сверяя с фрагментами — верность
источникам и цитаты — и с вашим `reference_answer` — полнота. Ответы и
вердикты хранятся в `data/eval-runs/<date>-<mode>-<label>/` (они цитируют
методички, поэтому в git не попадают); отчёт `reports/<date>-generation.md`
содержит только id и числа.

## Калибровка судьи

Судья хорош ровно настолько, насколько он согласен с человеком. Прочитайте
часть ответов в `data/eval-runs/<run>/answers.jsonl` и разметьте их в
`manual_labels.jsonl` — только сами, как и вопросы;
`manual_labels.example.jsonl` показывает формат:

| поле | смысл |
|---|---|
| `id` | id вопроса |
| `answer_run` | папка прогона, где лежит ответ, например `2026-10-05-hybrid+rerank-qwen3.5-9b` |
| `faithful` | каждое утверждение есть во фрагментах, которые получила модель |
| `complete` | ответ покрывает ваш эталонный ответ |
| `note` | необязательно, для себя |

    uv run nsu-rag eval --stage judge

печатает согласие судьи с вами и каппу Коэна отдельно для верности источникам
и для полноты и пишет `reports/<date>-judge.md`. Каппа поправляет на случайное
совпадение: судья, который всё называет верным, совпадёт с вами в 90% случаев,
если верны девять ответов из десяти, но получит 0. Примерно 30 размеченных
ответов — и число уже стоит читать.

## Агент против конвейера (фаза 5)

    uv run nsu-rag eval --stage agent

Обе системы отвечают на каждый вопрос целиком — сами ищут, без указания курса,
так, как спросил бы студент, — и судья оценивает обе одинаково. Отчёт
`reports/<date>-agent.md` добавляет то, что делает только агент: как часто его
маршрутизатор выбирал курс самого вопроса и сколько поисков ушло на вопрос.
По вопросам без ответа стоит настраивать порог отказа агента
(`AGENT_MIN_SCORE`).

## Полный корпус (фаза 4.5)

Те же вопросы к полному индексу отвечают на вопрос «не тонут ли ответы в
десятикратно большем объёме текста?»:

    uv run --env-file corpus.full.env nsu-rag eval --stage retrieval    # recall
    uv run --env-file corpus.full.env nsu-rag eval --stage generation   # верность источникам

(из корня репозитория) пишут `reports/<date>-retrieval-full.md` и
`reports/<date>-generation-full.md` рядом с отчётами MVP за тот же день.
Эталонные страницы в сканах, которые MVP не смог прочитать, на индексе MVP
считаются промахами и находятся только в полном индексе, поэтому сравнивайте
оба индекса и на вопросах, на которые индекс MVP в принципе мог ответить, и на
всех вопросах.
