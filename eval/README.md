# Evaluation questions

> Writing them: a step-by-step guide in Russian, [QUESTIONS_GUIDE.md](QUESTIONS_GUIDE.md),
> and a 60-slot skeleton to fill in, `questions.skeleton.jsonl`.

`questions.jsonl` is written by the author, one JSON object per line, and by
nobody else: questions generated by the system under test would measure
nothing. `questions.example.jsonl` shows the format with two placeholders.

| field | meaning |
|---|---|
| `id` | unique, e.g. `q001` |
| `course` | the course slug the question belongs to: `os`, `matan`, `tvims`… |
| `question` | as a student would ask it |
| `type` | `factual`, `definition`, `comparison`, `multi_hop` or `unanswerable` |
| `gold` | where the answer is: `[{"file": ..., "pages": [...]}]`; empty for `unanswerable` |
| `reference_answer` | the answer, in your own words |

* `file` is the path **relative to `data/raw/`**, as in `data/courses.yaml`:
  `os/sem4/<file>.pdf`.
* `pages` are the page numbers **of the PDF file, counting from 1** - what your
  viewer's page field shows - not the number printed on the page. The two
  differ whenever a cover or a table of contents comes first (ADR-011).
* A `multi_hop` question needs its answer from two or more places: list each.
* Only documents in the index can be found; the validator warns about a gold
  file that is not (outside the MVP, or a scan).

A useful set has at least ~50 questions: 10 per MVP course, a mix of types,
and around five `unanswerable` ones that sound plausible but are not in the
handbooks. With fewer, the confidence interval in the report is wider than
the differences between retrieval modes.

    uv run nsu-rag eval --stage retrieval --validate-only   # check the file
    uv run nsu-rag eval --stage retrieval                   # all four modes

Reports go to `reports/<date>-retrieval.md` and hold question ids and metrics
only - no question text and nothing quoted from the handbooks - so they can
be committed.

## Evaluating answers (phase 4)

    uv run nsu-rag eval --stage generation                     # every model in models.yaml
    uv run nsu-rag eval --stage generation --variants qwen3.5-9b --no-judge

Every question is searched once (`RETRIEVAL_MODE`, no course filter, as a
student would ask) and every model in `models.yaml` answers from the same
fragments, with the others unloaded. Then the judge (`JUDGE_*` settings) reads
each answer twice: against the fragments - faithfulness and citations - and
against your `reference_answer` - completeness. Answers and verdicts are kept
in `data/eval-runs/<date>-<mode>-<label>/` (they quote the handbooks, so they
stay out of git); the report, `reports/<date>-generation.md`, holds ids and
numbers only.

## Calibrating the judge

A judge is only as good as its agreement with a person. Read some answers in
`data/eval-runs/<run>/answers.jsonl`, and label them in `manual_labels.jsonl` -
yours alone, like the questions; `manual_labels.example.jsonl` shows the
format:

| field | meaning |
|---|---|
| `id` | the question's id |
| `answer_run` | the run directory the answer is in, e.g. `2026-10-05-hybrid+rerank-qwen3.5-9b` |
| `faithful` | every claim is in the fragments the model was given |
| `complete` | the answer covers your reference answer |
| `note` | optional, for yourself |

    uv run nsu-rag eval --stage judge

prints the judge's agreement with you and Cohen's kappa, for faithfulness and
completeness separately, and writes `reports/<date>-judge.md`. Kappa corrects
for chance: a judge that calls everything faithful agrees 90% of the time when
nine answers in ten are, and scores 0. Some 30 labelled answers make the
number worth reading.

## The agent against the pipeline (phase 5)

    uv run nsu-rag eval --stage agent

Both systems answer every question end to end - searching for themselves,
without the question's course, as a student would ask - and the judge rules
on both the same way. The report, `reports/<date>-agent.md`, adds what only
the agent does: how often its router picked the question's own course, and
how many searches a question took. Its unanswerable questions are where the
agent's refusal threshold (`AGENT_MIN_SCORE`) should be tuned.

## The full corpus (phase 4.5)

The same questions against the full index answer "does ten times more text
drown the answers?":

    uv run --env-file corpus.full.env nsu-rag eval --stage retrieval    # recall
    uv run --env-file corpus.full.env nsu-rag eval --stage generation   # faithfulness

(from the repository root) write `reports/<date>-retrieval-full.md` and
`reports/<date>-generation-full.md` next to the MVP's reports of the same day.
Gold pages in scans the MVP could not read count as misses on the MVP index
and can be found only in the full one - so compare the two on the questions
the MVP index could answer at all, as well as on all of them.
